# WHENMUSIC — 기술 스펙과 결정 기록

> 프로젝트 정의는 [01_프로젝트.md](01_프로젝트.md), 요구사항 ID는 [02_요구사항.md](02_요구사항.md). 2026-09-18 v0.1.
> 이 문서의 결정은 대부분 **2026-09-18 사용자 PC 실측**에 근거한다. 실측 원본은 [§12](#12-실측-로그).

## 1. 스택 (형제 앱과 동일, 하나만 다르다)

| | |
|---|---|
| 런타임 | Electron 43.x · Node 22+ |
| 렌더러 | vanilla JS + CSS. 프레임워크 없음 ([D-01](#d-01-스택은-형제-앱-계열이다)) |
| 저장소 | `node:sqlite` 단일 파일 (`store.sqlite`) |
| 글꼴 | 번들한 Pretendard Variable |
| **미디어 세션** | **[when630/node-windows-smtc-monitor](https://github.com/when630/node-windows-smtc-monitor)** — `@coooookies/windows-smtc-monitor` 포크 ([D-05](#d-05-애드온을-포크해-제어를-더한다) · [D-19](#d-19-애드온-포크는-별도-저장소에-둔다)) |
| 빌드 | electron-builder → Windows NSIS. 애드온은 GitHub Actions ([D-06](#d-06-애드온은-ci에서만-빌드한다)) |
| 배포 | GitHub Releases, 미서명, electron-updater |
| 테스트 | `node:test` + 창 없는 스모크 |

형제 앱과 다른 줄은 하나다 — **네이티브 애드온**. WHENNOTE·WHENCALENDAR·WHENWORK는 네이티브 의존성이 0이고 빌드 단계도 없다. 이 앱은 Windows SMTC에 붙어야 하므로 그 원칙을 처음으로 깬다. 대신 **개발 PC에는 툴체인을 두지 않는 것**으로 비용을 제한한다([D-06](#d-06-애드온은-ci에서만-빌드한다)).

## 2. 모듈 구조

```

  lifecycle.mjs    창 생성·트레이·자동시작
  card.mjs         코너 카드 창과 상태 브로드캐스트      ← 이 앱 고유
  smtc-worker.mjs  Worker thread. 애드온은 여기서만 만진다  ← 이 앱 고유
  session.mjs      세션 추적 · position 보간 · 이력 적재   ← 이 앱 고유
  control.mjs      제어 명령 한 곳. 교체 지점이다          ← 이 앱 고유
  stamps.mjs       도장 기록·되돌아가기
  store.mjs        SQLite 접근
  search.mjs       초성·질의 해석 (WHENNOTE 이식, 순수 모듈)
  ipc.mjs          채널 정의
  settings.mjs     설정
  place.mjs        창 위치 기억 (WHENWORK 승계)
  update.mjs       자동 업데이트 (WHENWORK 승계)
  platform/        OS 분기는 여기 안에만 (PLAT-06)
renderer/
  card.html/js     코너 카드
  main.html/js     이력 창 (이력 · 도장 · 설정 탭)
```

`control.mjs`가 **제어 구현을 감추는 유일한 경계**다. 지금은 포크한 애드온을 부르지만, 애드온이 막히면 이 파일만 갈아끼워 미디어 키나 PowerShell로 내려갈 수 있다([D-04](#d-04-제어는-세션-직접-명령이다)).

## 3. 데이터 흐름

```
 [Chrome / Spotify / 로컬 플레이어]
              │ SMTC (Windows)
              ▼
   smtc-worker.mjs  (Worker thread — 필수, D-16)
              │ postMessage
              ▼
   session.mjs ──── position 보간(§5) ──┬─→ card.mjs → 카드 렌더러
              │                          └─→ store.mjs (이력 적재)
              ▼
   control.mjs ──── TryPause / TryPlay / TrySkip / TryChangePlaybackPosition
              │
              └────────────────────────→ 다시 SMTC로
```

읽기와 제어가 같은 애드온을 쓰지만 **방향이 반대**다. 읽기는 Worker에서 이벤트로 흘러나오고, 제어는 메인에서 Worker로 요청을 보낸다.

## 4. 데이터 모델 (v1 스키마)

```sql
-- 관측한 재생 구간. 한 줄이 "한 번 들은 믹스"다 (HIST-03).
-- 곡 단위가 아니다 — SMTC가 1시간 영상을 한 곡으로 준다(§12).
CREATE TABLE plays (
  id            INTEGER PRIMARY KEY,
  source_app    TEXT    NOT NULL,   -- SMTC sourceAppId. 실측상 'Chrome' 수준까지만 온다
  title         TEXT    NOT NULL,   -- NFKC 정규화본. 검색·표시는 이걸 쓴다 (D-13)
  title_raw     TEXT    NOT NULL,   -- 원문 보존
  title_cho     TEXT    NOT NULL,   -- 초성 인덱스 (SRCH-02)
  channel       TEXT    NOT NULL,   -- SMTC artist. 유튜브에선 채널명이다
  channel_cho   TEXT    NOT NULL,
  duration_sec  REAL,               -- NULL이면 길이를 모른다 (라디오 스트림, CARD-12)
  thumb_id      INTEGER REFERENCES thumbs(id),
  started_at    INTEGER NOT NULL,   -- epoch ms
  ended_at      INTEGER,
  listened_sec  REAL    NOT NULL DEFAULT 0,  -- 앱이 실제로 관측한 시간 (STOR-02)
  last_pos_sec  REAL,               -- 이어 듣기 지점 (HIST-05)
  pos_trusted   INTEGER NOT NULL DEFAULT 0,  -- 보간 기준점을 잡았는가 (§5)
  deleted_at    INTEGER
);

-- 표시해 둔 한 순간 (STMP-03).
CREATE TABLE stamps (
  id           INTEGER PRIMARY KEY,
  play_id      INTEGER NOT NULL REFERENCES plays(id),
  pos_sec      REAL    NOT NULL,
  at           INTEGER NOT NULL,
  confirmed_at INTEGER,             -- NULL이면 아직 되짚지 않았다 (STMP-05)
  deleted_at   INTEGER
);

-- 썸네일은 내용 해시로 한 번만 저장한다 (STOR-03). 실측 약 23KB PNG.
CREATE TABLE thumbs (
  id   INTEGER PRIMARY KEY,
  hash TEXT NOT NULL UNIQUE,
  png  BLOB NOT NULL
);
```

`plays`를 나누는 규칙은 **제목·채널이 바뀌거나, 30분 넘게 끊겼을 때**다 (HIST-04). 같은 영상을 이어 들으면 한 줄로 합친다.

## 5. position 보간 — 이 앱의 핵심 난제

**SMTC의 `timeline.position`은 재생 중에 갱신되지 않는다.** 실측에서 3초 뒤에도 같은 값이었고, 기준값이 **8분(481초)까지 낡아** 있었다(§12). 상태가 바뀌는 순간에만 갱신된다.

```js
// 기준점 — playback/timeline 이벤트가 올 때마다 갱신한다
anchor = { posSec, atMs: Date.now(), status };

// 현재 위치 추정
function nowPos(anchor) {
  if (anchor.status !== PLAYING) return anchor.posSec;
  return anchor.posSec + (Date.now() - anchor.atMs) / 1000;
}
```

| 상황 | 신뢰도 | 화면 |
|---|---|---|
| 앱이 켜진 뒤 재생이 시작됐다 | **정확** | 위치·진행바를 그대로 보여 준다 |
| 이미 재생 중일 때 앱이 켜졌다 | **낡음** (최대 수십 분) | `pos_trusted = 0`. 위치를 흐리게 보여 주고 **도장을 막지는 않되 근사임을 표시**한다 |
| 사용자가 시크했다 | 정확 | `timeline-changed`가 오므로 기준점을 다시 잡는다 |

낡은 기준점은 **한 번의 상태 변화로 복구된다.** 일시정지·재생·시크 중 무엇이든 한 번 일어나면 정확해진다. 앱이 임의로 pause/play를 찍어 동기화하는 방법은 **쓰지 않는다** — 소리가 끊기는 것이 부정확한 숫자보다 나쁘다.

재생 속도 변경(1.25배 등)은 보간을 깨뜨린다. SMTC가 속도를 주지 않으므로 v1은 1배속을 가정하고, 시크가 일어나면 자연히 교정된다.

## 6. 카드 상태

| 상태 | 조건 | 표시 |
|---|---|---|
| `playing` | 세션 있음 · PLAYING | 기본 카드 (CARD-05) |
| `paused` | 세션 있음 · PAUSED | 색이 빠지고 흐려진다. 일시정지 아이콘을 띄우지 않는다 |
| `stale` | PLAYING이지만 `pos_trusted = 0` | 위치를 흐리게. 진행바는 보여 주되 시각에 `~`를 붙인다 |
| `stamped` | 도장 직후 1.4초 | 보라 강조. 자동으로 `playing`으로 돌아간다 (STMP-02) |
| `seeking` | 되감기 직후 1.4초 | 되감은 양을 글자로 (CTL-03) |
| `empty` | 세션 없음 | 안내를 8초 보여준 뒤 사라진다 (CARD-10) |
| `error` | 애드온 로드 실패 · OS 미지원 | 원인과 필요 조건 한 줄. 이력 창은 계속 열린다 (PLAT-03) |

`empty`가 **이 앱의 첫인상**이다. SMTC 세션은 재생이 시작돼야 생기므로 설치 직후에는 반드시 비어 있다.

## 7. 카드 창의 제약

whencalendar `main/overlay.mjs`와 같은 기법을 쓴다.

```js
frame: false, transparent: true, resizable: false, movable: false,
skipTaskbar: true, hasShadow: false, alwaysOnTop: true,
focusable: false,                              // 타이핑하던 창의 커서를 뺏지 않는다 (CARD-04)
win.setIgnoreMouseEvents(true, { forward: true });  // 클릭 통과 + 호버 수신 (CARD-03)
win.setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true });
```

- **z-order를 1초 주기로 다시 잡는다.** 없으면 전체화면 앱이 나중에 뜰 때 가려진다 (CARD-02)
- 창 크기는 카드 + 호버 여유를 포함해 **280×200**, 배치는 `screen.getPrimaryDisplay().workArea` 기준 우하단 여백 16px
- 버튼은 클릭을 받아야 하므로 `forward` 모드에서 마우스가 버튼 영역에 들어오면 `setIgnoreMouseEvents(false)`로 잠깐 바꾸고, 벗어나면 되돌린다
- `focusable: false`라 **스크린리더·키보드가 카드에 닿지 않는다.** 그래서 도장·되감기·재생에 전역 단축키를 반드시 둔다 (접근성 보상)

## 8. 제어 경로

포크에 더할 메서드는 여섯이다. 전부 `GlobalSystemMediaTransportControlsSession`에 이미 있는 것을 노출만 한다.

| 메서드 | 대응 요구사항 | 미디어 키로 가능? |
|---|---|---|
| `tryPlay(appId)` | CTL-01 | 토글만 |
| `tryPause(appId)` | CTL-01 | 토글만 |
| `trySkipNext(appId)` | CTL-02 | 대상 지정 불가 |
| `trySkipPrevious(appId)` | CTL-02 | 대상 지정 불가 |
| `tryChangePlaybackPosition(appId, sec)` | CTL-03 · CTL-05 | **불가 — 그런 키가 없다** |
| `getCapabilities(appId)` | CTL-07 | 불가 |

`Try*`는 **요청이 수락됨**만 의미한다. 실제 반영은 이벤트로 확인하고, 그 사이는 낙관적 UI가 메운다([D-14](#d-14-ui는-낙관적으로-먼저-바꾼다)).

## 10. 테스트·스모크·CI

- **순수 모듈은 `node:test`로** — 보간(§5), 세션 분할 규칙(HIST-04), 초성·질의 해석(SRCH), NFKC 정규화(D-13)
- SMTC는 **가짜 이벤트 스트림으로 대체**한다. 실제 애드온은 CI에서 재생 중인 세션을 만들 수 없다
- 창 없는 스모크(`--smoke`)로 부트·저장소·마이그레이션을 확인한다
- 애드온은 **별도 저장소·별도 CI**. 태그를 올리면 `windows-latest`에서 `.node`를 빌드해 릴리스에 붙인다

## 11. 결정 기록

### D-01 스택은 형제 앱 계열이다
Electron + vanilla JS + `node:sqlite`. 프레임워크·번들러를 넣지 않는다. 다섯 앱이 같은 구조여야 검증된 모듈을 옮겨 쓸 수 있다.

### D-02 재생 장치를 갖지 않는다
소리는 남의 앱이 낸다. 이 앱은 SMTC 층이다. 자체 재생을 넣는 순간 코덱·라이브러리·포맷 지원이 따라오고, 그건 MusicBee·AIMP가 이미 하는 일이다. 주 사용자에게 로컬 음원이 거의 없다는 사실도 같은 방향을 가리킨다.
**폐기안** — 로컬 파일 재생기(v1 초안). 사용자의 청취 형태가 스트리밍 전용이라 쓰지 않는 코드가 된다.

### D-03 곡 식별을 하지 않는다
1시간 믹스에서 지금 곡의 이름을 아는 경로가 셋 있었고 전부 버렸다.
- **SMTC 챕터** — 오지 않는다. 실측에서 `Subtitle`·`Genres`가 전부 빈 값이었다
- **설명란 타임스탬프 파싱** — videoId가 필요한데 SMTC가 주지 않는다. 타임스탬프가 없는 영상은 속수무책
- **오디오 핑거프린팅** — API 키·유료·상시 네트워크. "설치 파일 하나"와 정면으로 어긋난다

대신 **되감기**가 이 필요를 대신한다. 곡이 뭔지는 유튜브 화면이 알려주므로, 이 앱은 *그 지점으로 데려다 주기만* 하면 된다.

### D-04 제어는 세션 직접 명령이다
키보드 미디어 키(`keybd_event(VK_MEDIA_PLAY_PAUSE)`)로도 브라우저 재생이 제어됐다(실측 확인). 그러나 두 가지를 못 한다 — **대상 지정**(키는 Windows가 고른 세션으로 간다)과 **되감기**(그런 키가 없다). 둘 다 이 앱의 핵심 요구(CTL-03·CTL-04)라서 미디어 키를 주 경로에서 폐기했다.
**폐기안** — 미디어 키. `control.mjs` 뒤의 폴백으로는 남길 수 있다(애드온이 막힌 환경).

### D-05 애드온을 포크해 제어를 더한다
`@coooookies/windows-smtc-monitor@1.0.12`는 Rust + napi-rs, **MIT**, 읽기·이벤트는 검증됐다. 노출 API를 확인한 결과 제어 메서드가 **없다**(`getSessions`·`getCurrentSession`·`getSessionById` + 이벤트 6종). Windows SMTC API에는 `Try*Async`가 이미 있으므로, 포크해서 **노출만 더하면 된다**(§8). 밑바닥부터 만들지 않는다.
원저작자 표시와 MIT 문구를 유지한다(REL-05). 업스트림에 PR도 보내되, 반영을 기다리지 않는다(해당 저장소는 Issues·PR이 0건이다).
**폐기안** — `windows-media-sessions`(.NET exe 15MB 스폰): 제어 메서드가 아예 없다.

### D-06 애드온은 CI에서만 빌드한다
napi-rs의 Windows 빌드는 MSVC 링커를 요구한다. Rust 툴체인 약 1.5GB + VS Build Tools 약 4GB로 **용량 자체는 부담이 아니지만**(개발 PC 여유 372GB), 제어 메서드 6개는 한 번 만들면 거의 바뀌지 않는다. `windows-latest` 러너에는 MSVC가 이미 있으므로 **개발 PC에 툴체인을 두지 않는다**. 개발 반복이 느려지는 대가만 있고, 이 정도로 안 변하는 코드엔 맞는 거래다.

### D-07 position은 앱이 직접 보간한다
SMTC가 재생 중 위치를 갱신하지 않기 때문이다(§5, §12). 보간 기준점은 `playback-changed`·`timeline-changed`가 준다. **앱이 임의로 pause/play를 찍어 동기화하지 않는다** — 소리가 끊기는 것이 부정확한 숫자보다 나쁘다. 대신 `stale` 상태를 화면에 드러내고(§6), 한 번의 사용자 조작으로 저절로 복구되게 둔다.

### D-08 카드는 우하단에 고정한다
WHENCALENDAR가 상단 중앙 아일랜드를 쓴다. 두 앱이 한 트레이에 사는 이상 화면 위쪽은 임자가 있다. 하단은 작업표시줄·IDE 상태바가 있는 **이미 정보용으로 양보된 띠**라 침범 비용도 낮다. 좌하단 선택지는 설정으로 연다(CARD-13).

### D-09 블러는 6px, 덮개 대신 좌측 띠로 글자를 지킨다
썸네일이 **16:9 영상 커버이고 곡과 무관하다**(실측 150×83). 정보 슬롯의 가장 큰 자리를 정보가 아닌 것이 차지하므로 **배경으로 내린다**. 그런데 블러를 낮춰 썸네일을 알아보게 하면 이미지의 밝은 부분이 살아나 **글자 대비가 무너지고**, 덮개를 진하게 올리면 낮춘 이득이 상쇄된다.
해법은 전면 덮개를 걷고 **글자가 놓인 왼쪽만 진하게, 오른쪽으로 빠지게** 두는 것이다(`linear-gradient(100deg, .94 38%, .62 72%, .42)`) + 글자에 `text-shadow`. 진행바 바탕도 흰빛 대신 **검정 반투명**으로 바꿔야 이미지 위에서 보인다. 시안 비교는 `design/mockups/card-options.html` §0.
**남은 위험** — 매우 밝은 썸네일에서 `text-shadow`만으로 부족할 수 있다([오픈이슈 #3](#오픈이슈)).

### D-10 되감기는 10초
한 곡이 지나간 직후를 되짚는 데 필요한 양이다. 15초는 이전 곡으로 넘어갈 위험이 있고, 5초는 도입부를 놓친다. 설정으로 연다(CARD-13).

### D-11 주 동작은 되감기, 도장은 보조
"좋은 곡을 놓친다"를 푸는 방법이 둘이었다 — 지금 되감아 확인하거나, 도장을 찍고 나중에 되짚거나. **되감기를 주로 정했다.** 곡을 지금 확인하는 것이 직접적이고, 나중에 되짚는 경로는 소스 URL 문제([오픈이슈 #1](#오픈이슈))에 걸려 있다. 도장은 **되감을 여유조차 없을 때**의 보조로 남는다. 카드 버튼도 되감기가 첫 자리다.

### D-12 이력은 믹스 단위, 도장은 별도 탭
곡 단위 이력은 이 청취 형태에서 **하루 3~4줄만 쌓여** 성립하지 않는다. 한 줄을 "한 번 들은 믹스"로 바꾼다. 도장 목록은 답하는 질문이 다르므로("얼마나 들었나" vs "놓친 것 되짚기") 합치지 않고 **두 번째 탭**으로 공존시킨다. 확인 안 한 도장 수는 탭 배지로 알린다.

### D-13 제목은 NFKC로 정규화하되 원문을 남긴다
실측 제목이 `[𝐏𝐥𝐚𝐲𝐥𝐢𝐬𝐭] 우연히 듣고 반해버려서… 그냥 저장해버린 노래들 🎧🤍｜감성 힙합/R&B`였다. 유니코드 수학 볼드·이모지·전각 `｜`가 섞여 있어 **정규화 없이는 검색이 걸리지 않는다**. 표시·검색은 정규화본을, 저장은 원문도 함께 한다(`title` / `title_raw`).

### D-14 UI는 낙관적으로 먼저 바꾼다
제어 명령 수락은 약 5ms인데 **SMTC 상태 반영은 그보다 늦다** — 실측에서 `pause` 직후 조회가 아직 `Playing`이었다. 버튼을 누르면 카드를 먼저 바꾸고, 이벤트가 오면 맞춘다. **어긋나면 이벤트 값이 이긴다.**

### D-15 SMTC 이벤트는 디바운스한다
실측에서 `playback-changed`가 **같은 상태로 두 번** 왔다. 상태 전이가 아닌 중복 이벤트는 버린다. 이력 적재가 이벤트 수에 비례하므로 이걸 놓치면 기록이 부풀어 오른다.

### D-16 SMTC는 Worker thread에서만 만진다
애드온 문서가 Electron에서 Worker thread 사용을 요구한다 — 메인·렌더러에서 직접 쓰면 프리징한다. `smtc-worker.mjs` 밖에서는 애드온을 `require`하지 않는다.

### D-17 다섯 앱은 코드를 공유하지 않는다
모노레포·공용 패키지를 만들지 않는다. 검증된 모듈을 **복사해** 시작하고 각자 진화한다 — `search.mjs`(WHENNOTE), 오버레이 창 기법(WHENCALENDAR), `place.mjs`·`update.mjs`(WHENWORK). 공유하는 것은 스택·구조·토큰·파이프라인·테스트 방식이다.

### D-18 상주 PowerShell 제어를 쓰지 않는다 (폐기안)
PowerShell의 WinRT 투영으로도 대상 지정과 절대 시크가 **전부 동작했다**(실측). 단발 호출은 약 250ms였지만 프로세스를 상주시키면 **제어 5.1ms · 조회 0.2ms**까지 떨어져 응답성은 충분했다. 버린 이유는 **메모리**다 — 상주 호스트가 WorkingSet 89.1MB / Private 65.8MB를 쓴다. `powershell.exe`는 WinRT를 쓰려면 .NET CLR을 띄워야 해서 줄일 방법이 없다. "평소엔 화면 3px만 쓴다"고 말하는 형제 앱 옆에서 음악 컨트롤러가 90MB를 상시 점유하는 그림이 맞지 않았다. 애드온은 +1MB다.
실행 정책(AppLocker)·안티바이러스 리스크도 함께 사라진다. **애드온이 막히는 환경에서는 이 경로를 폴백으로 되살릴 수 있다** — `control.mjs`가 그 교체 지점이다.

### D-19 애드온 포크는 별도 저장소에 둔다 (2026-09-18)
포크를 whenmusic 저장소 안(`native/`)에 두면 버전이 항상 맞물리지만, **whenmusic 릴리스마다 Rust 빌드가 돈다**. 애드온은 제어 메서드 6종을 더하고 나면 릴리스 주기가 본체와 전혀 다르므로 분리한다.

포크 완료: **[when630/node-windows-smtc-monitor](https://github.com/when630/node-windows-smtc-monitor)** (2026-09-18, MIT 유지, upstream `LeagueTavern/node-windows-smtc-monitor`).

저장소 이름은 **원본 그대로 둔다** — 무엇의 포크인지가 이름에서 드러나야 업스트림 변경을 따라갈 때 혼동이 없다. 배포 방식(npm 퍼블리시 vs GitHub 릴리스의 `.node`를 직접 받기)은 Phase 1에서 정한다.

### D-20 애드온은 npm에 퍼블리시하지 않고 릴리스의 `.node`를 쓴다 (2026-09-18)
[오픈이슈 #5](#오픈이슈)의 결정이다. npm 퍼블리시는 계정·토큰·스코프 패키지 관리가 따라오는데, 얻는 것은 `npm i` 한 줄뿐이다. 애드온은 제어 메서드 6종을 더하고 나면 **거의 바뀌지 않으므로**([D-06](#d-06-애드온은-ci에서만-빌드한다)) 그 편의가 관리 비용을 못 넘는다.

포크 저장소는 태그를 올리면 세 타겟(`x64`·`ia32`·`arm64`)을 빌드해 `.node`를 릴리스에 붙인다(`.github/workflows/release.yml`). whenmusic은 x64 바이너리를 **저장소에 직접 커밋**하고 electron-builder가 그대로 패키징한다. 설치·빌드 어디에도 네트워크와 Rust가 끼지 않는다 — "설치 파일 하나"와 같은 방향이다.
**폐기안** — npm 스코프 퍼블리시(`@when630/windows-smtc-monitor`). 되살릴 여지는 남는다. 업스트림이 PR을 받아 주면 그쪽 npm 패키지로 돌아가는 것이 가장 깨끗하다.

### D-21 썸네일은 내보내기에 담지 않는다 (2026-09-18)
실측 썸네일이 줄마다 약 23KB다. 하루 서너 줄씩 1년이면 1,500줄이고, base64로 부풀면 내보내기 파일이 **수십 MB**가 된다. JSON 하나로 주고받는다는 것(DATA-01)이 그 크기에서는 성립하지 않는다.

썸네일은 **같은 영상을 다시 들으면 SMTC가 다시 준다.** 잃어도 되는 유일한 자료라서 뺀다. 가져온 줄의 `thumb_id`는 `NULL`이고, 다음에 그 믹스를 들을 때 다시 붙는다.
**폐기안** — 별도 파일로 함께 내보내기(zip). "파일 하나"가 깨진다.

### D-22 스쳐 지나간 줄은 이력에 남기지 않는다 (2026-09-21)
2026-09-21 실측에서 믹스를 듣는 중에 **다른 미디어가 2초 동안 SMTC 세션을 가로챘다.** 제목 `Miss your voice` · 채널 `Tokyo Lyric - Topic`(유튜브 자동 생성 채널) · 길이 599초 — 듣던 믹스(4,258초)와 **제목·채널·길이가 통째로 달랐다.** 곧 원래 믹스로 돌아왔다.

[HIST-04](02_요구사항.md) 규칙은 제목이나 채널이 바뀌면 새 줄로 나눈다. 그래서 이런 전환마다 **2초짜리 줄**이 하나씩 쌓이고, 하루 서너 줄이어야 할 이력([D-12](#d-12-이력은-믹스-단위-도장은-별도-탭))이 쓰레기로 덮인다.

**20초 미만으로 관측한 줄은 남기지 않는다.** 줄이 닫히는 순간(다음 줄로 넘어갈 때) 지우고, 그 사이에 앱이 꺼졌으면 다음 부팅에서 치운다. 사용자가 지운 것이 아니므로 소프트 삭제([STOR-04](02_요구사항.md))가 아니라 아예 없앤다 — 되살릴 이유가 없고, 휴지통에 쌓이면 그것도 쓰레기다.

**예외는 도장이다.** 2초를 들었어도 표시해 뒀다면 그건 의미가 있다.
**폐기안** — 이력 조회에서 숨기기만 하기. DB에는 계속 쌓이고, 내보내기 파일에도 실린다.

## 오픈이슈
